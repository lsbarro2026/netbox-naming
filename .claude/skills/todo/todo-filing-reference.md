# `/todo` — reference material, loaded on demand

`.claude/skills/todo/SKILL.md` points here from five places — one in step 2, four in step 3 — each
gated on a condition it states before the pointer. **Read only the section you were sent to**; the
others are unrelated.

## One item or several

**One item per independently landable result.** A piece nobody would land on its own isn't an item,
it's a step — put it in the body as a step and file one item.

Four signals say **split** (any one is enough, provided each piece clears the "landable alone" bar):

- **Two acceptance sentences.** You can't write "done when …" without an "and" joining two unrelated
  conditions.
- **Two routes on different models.** Routed honestly, the pieces land on routes that run on
  different models. An item carries one route and goes to exactly one model, so a `trivial` doc fix
  welded to a `judgment` refactor either burns a large-model tab on the doc fix or hands the refactor
  to a small-model tab. This is the split signal most often missed, and the cheapest to check — you
  answered the route questions anyway.
- **One piece decides what another must target** — a design/decision step and the work built on it.
  Split **and** order them (see *Classifying the item*); this is the one case where splitting adds an
  ordering constraint rather than removing one.
- **Two tabs could work them at once** — disjoint files, no shared invariant. Splitting buys real
  parallelism.

Three say **keep it one item**:

- **A piece nobody would land alone.** "Add the flag" + "document the flag" is one item; nobody ships
  half of it.
- **One invariant spans the pieces.** A parser change and its call sites are verified together or not
  at all; split them and `main` holds a half-applied change between the two lands.
- **Both are tiny and in the same place.** Every item pays a fixed claim → plan → worktree → commit →
  `land` → teardown cycle that dwarfs a `trivial` edit, so two of those in one file cost less as one
  item than as two.

**This is `/reorder`'s merge test read backwards.** `/reorder` step 3 folds duplicates, split halves,
and `trivial` items sharing a file back into one item. If the set you're about to file is a set
`/reorder` would fold back together, file it as one item now. Symmetrically, don't split to make items
*look* smaller: the route is declared with `--route`, not inferred from how many items you filed.

A multi-part feature whose parts each need research and a plan before anyone builds them is a job
for `/todo-expanded`, not a batch of items here: suggest it to me rather than filing it here.

## Route examples

You're here because `/todo`'s four questions left you between two routes. Each boundary below has
labelled examples; find the one closest to your item. A route's model buys judgment, its effort
buys diligence: pick the model by the hardest single decision in the item, the effort by how much
there is to check.

**`trivial` | `routine`** — does the whole diff fit in one sentence?
- `trivial`: fix a typo in the `--help` text of one command.
- `trivial`: bump the pinned version of one dependency, lockfile regenerated by the tool.
- `trivial`: a default timeout is 3 s where the docs say 30 s; change the constant and its test.
- `routine`: add a `--quiet` flag to one command, threaded into its logger, with a test.
- `routine`: a known null-pointer in one handler, whose fix needs a guard and a new error message.

**`routine` | `standard`** — how far does it spread?
- `routine`: a new column in one report and its test (two files).
- `routine`: validate one config key in the loader, following the existing validator.
- `standard`: an import option threaded through the parser, the model and three views, its
  behaviour fully specified in the request.
- `standard`: a new endpoint following an existing one: route, handler, schema, client, tests.

**`standard` | `wide`** — is the spread mechanical?
- `standard`: a feature across six files, each needing its own small design within a settled plan.
- `wide`: rename a function and all ~40 call sites, with a test suite to prove it.
- `wide`: migrate every test file from one assertion style to another.
- `wide`: add type annotations to one package, checked by the type checker.

**`standard` | `judgment`** — is anything open, risky or unprovable?
- `standard`: a retry wrapper around one client, backoff numbers given in the request.
- `judgment`: the same wrapper, but which calls are safe to retry is not yet known.
- `judgment`: a crash with no known root cause, however small the eventual fix.
- `judgment`: a two-file change to how a lock file is taken (concurrency is a risky invariant).
- `judgment`: a UI change that only a person can verify, with no command to prove it.

**`judgment` | `deep`** — does the open question span many files?
- `judgment`: choose between skipping or parking bad rows in one importer.
- `judgment`: change one public API's error contract and its handful of callers.
- `deep`: unify error handling across a dozen modules, the shared error type still undecided.
- `deep`: replace the cache layer used across a dozen modules, invalidation rules undecided.

**`deep` | `frontier`** — is the open decision the architecture itself?
- `deep`: a cross-module feature with open questions inside an architecture that stays.
- `frontier`: split the in-process job runner out into a service with its own queue.
- `frontier`: replace the sync protocol with a different consistency model, migration included.
- `frontier`: an ambiguous goal ("make sync reliable") that needs long autonomous investigation.

Split → file the set with `add-bulk` (*Filing several items at once*), and ask *Classifying the item*
whether the pieces also need ordering. Not split → plain `add`.

## Classifying the item: admin, priority, critical, blocked

Ordinary code work is a plain `add` and never reaches this section. For the rest, **reach for the
weakest tool that gets the ordering right** — each step down this ladder costs other tabs more:

| What you want | Tool | What it costs everyone else |
|---|---|---|
| worked eventually, in the order filed | plain `add` | nothing |
| worked only after another item lands | `--blocked-by <ID>` | this item's own parallelism |
| worked before the rest of the queue | `--priority` | one claim cycle for every other tab |
| nothing else worked at all until it lands | `--critical` | the whole queue — every tab, every tier |
| done by a human, never by an agent | `--admin` | nothing (never auto-claimed) |

**"Must land after X" is `--blocked-by X`, never `--priority`.** This is the common misuse worth
naming: priority controls *when this item is claimed*, not what it comes *after*, so marking a
dependent priority gets it claimed **first** and built against the state it was supposed to wait for.

- **Human-only** (publish, grant access, flip a repo setting, buy/sign something) → add it to the
  **Admin** section with `--admin` (use an `ADMIN-<n>` id via `next-id ADMIN`). `/plan-todo` will
  never claim it; the user completes it with `/admin-task`, or is walked through it by
  `/work-admin-task`.
- **Must wait for another item** → `--blocked-by <ID>`. The test is the one `/reorder` applies, so
  filing and reordering can't contradict each other:

  > **Would this item be planned or built differently if whoever claims it could see the other
  > item's finished result?** If yes, block it behind that item. If the result would merely be
  > interesting context — or the two just share a topic, a subsystem, or a word in their titles —
  > leave it unblocked.

  Bias against blocking, harder here than in `/reorder`: a block costs real parallelism (the
  dependent sits unclaimable while its blocker is planned, implemented and finished), and filing
  time is when you know **least** — you see one request, not the whole backlog. `/reorder` adds
  chains later with the entire graph in view, and does it reversibly. Three mechanics worth knowing:

  - **Blocking on an `in_progress` item is legal and often right** — `add` requires the blocker to
    exist, not to be unclaimed — and the gate clears on its own: `/finish`'s `land` removes the
    blocker, and `next` strips the orphaned marker. This is the answer when your item needs the
    result of work already in flight (you can't `append` to a claimed item — see step 2). What you
    can't do is `block` an item that is *itself* claimed (like `edit`/`append`, it would never reach
    the worktree).
  - **A blocker id must match an existing item.** `add`, `add-bulk` and `block` refuse an id that
    matches nothing and write nothing, so a typo'd id fails loudly instead of quietly not gating.
    Within a single `add-bulk` batch a forward reference to a later item is fine — the batch
    validates as a set. (`doctor` still reports a marker that went dangling by hand-editing.)
  - **Gates can't cycle.** `add`, `add-bulk`, `block` and `reorder` each refuse a cyclic chain and
    write nothing; `doctor` reports one that was hand-edited in. If you hit that refusal, `/reorder`
    is what re-cuts the chain.
- **Code work that can't start until a human does something** → add it to Open **linked to the Admin
  task** with `--blocked-by <ADMIN-ID>` (creating the Admin task first if none fits). That stamps
  `[BLOCKED: <ADMIN-ID>]` on it, so `/plan-todo` skips it until the human runs `/admin-task`, which
  unblocks it. Every human-gated blocked item should have such an Admin task. The reverse is legal
  too: an **Admin** task may itself be `--blocked-by` an Open item (a human check that must wait
  for code to land); the marker clears when that item is finished.
- **Urgent — must be picked up before any other item** → `--priority`. The test: **does the rest of
  the backlog get worse while this waits?** Yes — a regression on `main`, breakage in tooling the
  other tabs depend on, or a small prerequisite several queued items would each work around. No —
  "the user sounded urgent", "this is important", "this is quick": ordinary importance is what file
  order already carries, and `/reorder` can re-order without spending the flag. Mechanically, `next`
  hands a priority item to the first free `/plan-todo` tab ahead of every non-priority item (multiple
  priority items keep their relative order), and it leads the `## Open` section in `summary` with
  status `priority`. Cannot combine with `--admin` (an Admin task is never auto-claimed, so priority
  is meaningless there). It **can** combine with `--blocked-by`: the item stays gated, and once the
  gate clears it is claimed ahead of the plain queue. Marking everything priority just rebuilds the
  plain queue one tier up.
- **Critical — the whole queue must freeze until this one thing lands** → `--critical`. The test:
  **would any item claimed before this lands be wasted or wrong work?** Only then. If the honest
  answer is "no, just slower", it's `--priority` at most. **Ask the user before filing one** — it
  stops tabs they may already have running. A much bigger hammer than `--priority`: while an
  unblocked `--critical` item exists and hasn't been `/finish`ed, `next` refuses to hand out
  *anything else at all*, to *any* tab or tier — even a matching-tier item that would otherwise be
  claimable — until this item is claimed and finished (`next` reports `BLOCKED-BY-CRITICAL <id>` to
  every other caller in the meantime). Cannot combine with `--admin`/`--blocked-by` (same reasoning
  as `--priority`) or with `--priority` itself (critical already outranks it — redundant).

## Overlap with work already in the backlog

`next` steers parallel tabs away from items whose declared files overlap an **active claim**, but
nothing compares two *unclaimed* items — so filing is where a foreseeable collision gets recorded.
One call shows the whole picture, without reading a body:

```
python3 .claude/todo-lock.py files
```

One line per Open item — `id · status · declared files · title`, read from each item's `**Files:**`
bullet. Spend it when your item will name a hot/shared path or when you're filing a set; skip it for
an ordinary item in its own corner of the tree.

**Documentation paths are soft.** Two items that share only documentation overlap harmlessly — git
merges docs cleanly — so a path under a `doc_dirs` directory (`.claude/todo-config.json`) or named in
the item's `**Docs:**` bullet is marked `[doc: …]` in the `files` line, and an overlap where both
sides are docs is informational: it never defers an item in `next`, never raises `⚠ HOT-FILE`, and
`conflicts` prints `DOC-OVERLAP` and still exits 0. Don't block or chain on a `[doc: …]` path alone.
A path that is also hot (`hot_files`/`hot_dirs`, or `CHANGELOG.md`) stays hot. Keep `**Docs:**` to
docs the item edits — the bullet's paths count as soft whether or not they sit in a `doc_dirs`.

Three outcomes:

- **Large overlap with an `open`/`priority` item** — both would substantially rewrite the same file →
  `--blocked-by <that-id>`, so the two land in sequence and neither eats a merge conflict. Same
  answer, same reason as `/reorder`'s same-file chaining.
- **Large overlap with an `in_progress` item** — file the new item (never `append` to a claimed one),
  note the relationship in the body (`- **Relates to:** <id> (in progress) — <how>.`), and add
  `--blocked-by <that-id>` if your item genuinely needs the other's result; the gate clears when that
  item lands.
- **Small or incidental overlap** — leave it to race. `/finish` resolves the merge on the branch,
  never on `main`, and over-blocking serializes work two tabs could do at once. Just make the
  `**Files:**` bullet accurate: `next` uses it to defer this item while the other is claimed, which
  is the whole mechanism, and `/reorder` can chain it later if the collision turns real.

**Filing-time overlap is advisory by design — don't try to make it a gate.** `add` records work; it
must never refuse it. And `next`'s check compares against active claims *only*, deliberately: two
unclaimed items naming the same file have nothing to collide with yet and may never be claimed at
once, so gating on that would defer work over a conflict that doesn't exist. The authoritative pass
is `/reorder`, which sees the whole graph and is reversible. (The same note lives next to
`_claim_overlap` in `.claude/todo-lock.py`, for whoever is tempted to widen it.)

## Filing several items at once (`add-bulk`)

When the request genuinely decomposes into more than one well-scoped item (*One item or several*
above is the test), file them with **`add-bulk`** rather than running `add` N times: it takes the
whole set as a JSON array on stdin and writes it in **one atomic store write**, so you never get half
a batch — one bad item writes nothing and exits non-zero. Everything in `/todo` still applies **per
item**: the step-2 dedup pass covers the whole set, each item gets its own honest `"route"`, each
body is shaped to `.claude/skills/todo/todo-prompting-guide.md` (the common part and the section for its route's
model), and every body carries the base skeleton (`**What:**`, `**Why:**`, `**Request:**`, `**Files:**`,
`**Docs:**`, `**Acceptance:**`, `**Open questions:**`, `**Plan:**`, `**Source:**`).

```
python3 .claude/todo-lock.py add-bulk --family FEAT --commit <<'EOF'
[
  {"title": "<concise title>",
   "body": "- **What:** …\n- **Why:** …\n- **Request:** \"…\"\n- **Files:** `a.py`.\n- **Docs:** none.\n- **Acceptance:** …\n- **Open questions:** none.\n- **Plan:** fast.\n- **Source:** …",
   "route": "routine"},
  {"title": "<concise title>",
   "body": "- **What:** …\n- **Why:** …\n- **Request:** \"…\"\n- **Files:** `b.py`.\n- **Docs:** `docs/x.md#y`.\n- **Acceptance:** …\n- **Open questions:** none.\n- **Plan:** full.\n- **Source:** …",
   "route": "judgment"}
]
EOF
```

Where a heredoc is refused (inside a worktree), write the JSON array with the Write tool and pass
`--file <path>` instead of the heredoc.

- **`--family <FAMILY>`** numbers the items off the same monotonic counter `next-id` uses, so you
  don't call `next-id` once per item. An item's own `"id"` always wins over it — that's how to mix
  families (say a `BUG` and two `FEAT`s) in one batch.
- **`--chain`** is the ordering mode: each item after the first is stamped
  `[BLOCKED: <previous-id>]`, so `/plan-todo` hands them out **one at a time in the declared
  order**. Reach for it when the items are **stages of one change** that must land in sequence — the
  same gate, and the same *"would this be built differently if it could see the other's result?"*
  test, as `--blocked-by` (*Classifying the item*), without you writing the ids. Independent items
  (the default, no flag) is the common case: chain the stages of one change, not every batch that
  happens to be filed together. A chained item can't be `"priority"`/`"admin"` — the chain fixes each item's
  place in the order — so file either of those separately.
- Per-item fields mirror `add`'s flags exactly: `"admin"`, `"priority"`, `"blocked_by"`,
  `"route"`. Bodies are JSON strings, so bullets are separated by `\n` and the inner quotes of the
  `**Request:**` bullet are escaped `\"`.
- **Don't reach for it to split one item into several.** Bulk files work you'd have filed anyway;
  a single item still goes through plain `add`.
